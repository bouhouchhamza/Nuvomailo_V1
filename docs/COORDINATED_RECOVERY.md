# Isolated coordinated recovery

Updated 16 October 2026. Executed only on synthetic lab data, into separate empty named volumes. No original volumes were overwritten or deleted, no external backup destination selected and no production RPO/RTO claimed.

## Snapshot and trust boundary

The operator runner rejects active lab worker services, stops mail/native broker and takes a native PostgreSQL custom dump. A no-network maintenance helper mounts source volumes read-only and includes database, mail/config/state, remote generation journals, synthetic credential encryption key, private worker/broker tokens and TLS material. It excludes earlier snapshot directories and runtime sockets/FIFOs; regular queued messages remain included. Links and device files are rejected. Restore requires empty destination volumes and an empty separate database; it rejects archive traversal, links/special entries and manifest mismatches before accepting data.

The tar is signed with a pinned synthetic certificate, then encrypted using native OpenSSL CMS AES-256-GCM and RSA-OAEP/SHA256. Verification uses the pinned external certificate and explicit trust file before extraction; decrypted data remains in a private tmpfs. Native CMS supports signing/encryption and GCM AEAD; this uses its standard format rather than a custom cryptographic protocol. [OpenSSL CMS documentation](https://docs.openssl.org/3.0/man1/openssl-cms/). The local seven-day backup key/certificate live in a separate restricted named volume and are never supplied as argv values. Production signer/recipient separation, KMS custody/rotation and recovery access are owner decisions.

## Commands and limits

Build backend/lab worker with current migrations, then run `node infrastructure/mail-lab/run-coordinated-backup.mjs`. It quiesces the lab, creates a fresh restore project, verifies restore and stops databases. Cold boot of the current snapshot: `node infrastructure/mail-lab/run-cold-recovery.mjs 4326d344-dbc7-4b16-9609-cf09b2580554`. Secret fixture values travel only through captured process pipes/stdin; output contains sanitized evidence. Never run these fixture commands against production or use restore targets containing data.

The maintenance helper needs bounded filesystem ownership capabilities on its isolated destination mounts; it is not a network service or a production agent. It verifies AEAD/signature completely before extraction and constrains manifest names to validated archive files. It has no Docker socket. The operator scripts control Docker outside application processes.

Remaining production work: consistent online/PITR strategy and WAL retention, agreed RPO/RTO and measured drill schedules, independently secured off-host storage, backup origin/key custody, retention, storage monitoring, queue replay during mismatched restore points, transport/filtering/abuse recovery and upgrade/rollback drills. Real destinations, paid storage, retention policy and production access remain approval-gated. Local free disk measured about 19.8 GiB after this drill; retained images, volumes and evidence were not pruned.
