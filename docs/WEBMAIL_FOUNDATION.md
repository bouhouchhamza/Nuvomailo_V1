# Authorized webmail foundation

14 October 2026. Implemented and tested against the isolated DMS lab only. The default application has no webmail provider. No public ports, real mailbox password or live delivery were enabled.

## Authorization and credential boundary

16 October send reconciliation: additive migration 4761 records only a fixed user-reported resolution and timestamp. The bound mailbox user with current write access can idempotently resolve their own uncertain attempt; changing the reported resolution conflicts. Resolution appends an audit event, removes the attempt from unresolved platform attention and leaves SMTP state `uncertain`. The original send key can never submit again. A missing Sent copy does not establish delivery failure; users must check with recipients before any deliberate new send. No provider-confirmed delivery claim is inferred from this action. Development has 4761; the accepted closed/recovery evidence still ends at 4760.

Migration 4742 adds explicit per-mailbox read/write assignments. Organization ownership does not automatically grant message access. Owners may assign active verified members through the tenant API. Each protocol operation rechecks membership, active organization/domain/user, verified domain, explicit local-lab activation and active desired mailbox status. Write permission is required for composing, flags, folder creation and moves to Trash. Changes already admitted to the provider may finish while access is revoked; distributed cancellation and stronger revocation barriers remain production work.

Dashboard and mailbox credentials are separate. A persistent authenticated dashboard session is required to connect. The API validates a separate synthetic mailbox password against IMAP, then encrypts it in process memory with AES-256-GCM, a random process key and user/session/mailbox-bound AAD. An opaque random token is stored only as a digest in memory and sent only in an HttpOnly, SameSite Strict cookie scoped to `/api/webmail` (Secure in production). Entries expire after 15 minutes and cannot survive process restart. No mailbox secret enters a job, audit record or reusable provisioning result. Memory encryption is not protection against compromise of the running process; strings passed to protocol libraries cannot be reliably erased by JavaScript.

Mutations require the custom CSRF header and reject foreign origins/cross-site fetches. Session binding prevents another dashboard session or user from reusing the cookie. Mail session expiry is a conflict requiring reconnection, separate from dashboard authentication expiry. Attachment responses force octet-stream, nosniff and a sanitized download filename.

## Implemented protocol and UI behavior

The lab adapter uses maintained ImapFlow, Nodemailer/MailComposer, Mailparser and sanitize-html packages. Hostnames and ports are fixed trusted configuration; synthetic address/recipient allowlists prevent external lab sending. IMAP uses verified TLS on 993; submission requires STARTTLS on 587 with certificate verification. The worker receives only the lab public certificate in a separate read-only volume, never the TLS private key or synthetic seed. IMAP and composition concurrency are bounded, protocol logs are disabled, errors are sanitized and raw sources/MIME/search windows are bounded.

Implemented operations include folders, folder creation, bounded UID-based pagination/search, message reading, attachment download, read/unread flags, retained moves to Trash, sending, Sent copies and Drafts. UIDVALIDITY must match before acting on a selected message. No permanent deletion exists. Compilation explicitly strips Bcc headers from the raw message while preserving Bcc envelope recipients. HTML removes scripts, images, styles, navigation and attributes; the UI renders its optional HTML preview in a sandboxed frame with a restrictive CSP. Plain text is displayed through React escaping.

The dashboard provides explicit connection/disconnection, mailbox access assignment, folders/search/pagination, message reading, attachments, replies, compose and attachments, draft save and retained Trash actions. Read-only users receive no sending controls. The password field clears on submission and is never placed in browser persistent storage. The unavailable default state has no password/send form. Revised-copy draft editing, mailbox/user-scoped contacts and bounded References/In-Reply-To conversation grouping are implemented. Rich composition, forwarding and a mailbox-wide thread index are not implemented.

SMTP acceptance is distinct from final delivery. Unexpected send errors report an uncertain outcome and must not trigger an automatic send retry. Accepted messages whose Sent append fails return an explicit accepted-without-copy outcome. Partial RCPT acceptance returns accepted/rejected recipient lists and the UI warns against resending to accepted recipients. This partial-rejection branch still needs a controlled rejection integration fixture: the actual lab's authenticated submission accepted an unknown local recipient at RCPT, so the experiment does **not** establish rejection or delivery for that unknown address. The successful internal delivery assertion uses the known pilot mailbox only. Bcc metadata is stripped from Drafts/Sent copies too; restoring a draft's hidden recipient list requires a separate private metadata design.

Credentials, protocol diagnostics and provider errors are suppressed; failure reports contain only a trusted stage/code. 15 October continuation: migration4756 adds personal contacts scoped jointly to the connected mailbox and dashboard user. Listing/upsert/delete requires the bound short-lived webmail session and rechecks current mailbox access; another assigned user receives an independent contact set even for the same address. The UI can add/remove contacts and copy a contact into the composer. Contacts remain control-plane metadata and are not synchronized to CardDAV or the provider.

Migration4757 adds a durable SMTP send-attempt ledger. The browser retains a UUID while an unchanged send is unresolved, and the server binds it to the actor, mailbox and SHA-256 digest of the validated message. A completed replay cannot submit SMTP twice; changed content under the same key is rejected. A provider error, crash-window replay or stale processing record becomes `uncertain` and is never automatically retried. Accepted state stores only copy status and recipient counts; subjects, bodies, attachments, recipient addresses and credentials are not persisted. Unresolved attempts appear in platform queue health. A mailbox user can now read the latest 50 content-free summaries after reconnecting, so a browser restart does not hide an uncertain outcome. Controlled tests previously passed for accepted replay, mismatched content, uncertain outcomes, tenant/user contact isolation and runtime-role denial; the newest summary/thread/attachment assertions are source-complete but await execution under the disk gate below.

Latest source continuation adds deterministic opaque thread identifiers derived from bounded References/In-Reply-To roots. Equal subjects without reference ancestry remain separate, and each response labels only the messages visible in its current 50-row page. The server fetches at most 64 KiB of the References header, retains at most 50 message IDs and never performs an unbounded mailbox scan. Attachment validation now enforces the advertised 1 MiB decoded-byte limit as well as canonical base64, five-file, filename and message-size bounds. Replayed partial acceptance continues to show rejected counts even though recipient addresses are deliberately absent from the durable ledger. A dependency-free Chromium scenario covers threads, persisted uncertainty, a contact recipient, attachment draft, explicit fresh-key reconciliation and partial acceptance against intercepted synthetic APIs.
