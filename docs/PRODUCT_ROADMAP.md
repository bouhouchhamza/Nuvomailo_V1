## Scope and evidence

Customer-facing applications include customer/organization dashboards, isolated platform administration and maintained webmail. Control-plane scope includes identity, tenants, domain/readiness, mailbox/credential/retention lifecycle, aliases/policies, entitlements/billing, audit and support. Async scope includes transactional outbox, typed jobs, leases/retry/dead letters, reconciliation, scheduling/deprovisioning/migration and telemetry. Mail-plane scope includes transport/storage/TLS/auth/filtering/signing/reputation/abuse. Operations includes secrets, isolation, observability, backup/recovery, privacy/retention, incidents, support and measured capacity.

Baseline tests prove local API flows and simulated DNS/jsdom outcomes; they do not establish mail function, production security, recovery, billing or capacity. Existing 100/200 MB ceilings are development policy, not a permanent commercial plan design or disk reservation. This roadmap supersedes demo-only scope in old documents.

Each milestone report must record changes/rationale/tests/migration risks/development-vs-production status/remaining work/next milestone. A milestone accepted locally is not a commercial release. No public DNS, VPS services, live emails, production deployment, spending or sensitive credential infrastructure changes without explicit authorization; prepare concrete proposals first.

## Iteration milestone report

### M3 isolated candidate spike

Owner-approved DMS-only local conformance is implemented and executed: pinned isolated environment, restricted Unix agent/explicit lab adapter, runtime quota/authentication inspection, durable remote revision/idempotency fencing, partial/crash/restart/reconciliation tests, aggregate quota enforcement, suspension/restoration, hash-compatibility experiment and cold restore on separate empty volumes. See [evidence](DMS_CONFORMANCE_RESULTS.md).

This satisfies the local candidate spike, not the entire M3 production integration acceptance. Production credentials/agent least privilege, real provider selection, receiving policy, filtered load, network/TLS/DNS/deliverability and off-host recovery remain decision-required/infrastructure-dependent. Raw Node Argon2 encoding compatibility failed until parameter ordering was canonicalized in the synthetic probe; this remains a reviewed-design issue. M4–M10 remain open.

M0 is complete with an actual-code audit, full-product target/dependencies, risks and documented tradeoffs. M1 adds transactional membership-lock authorization/audits, correlated safe HTTP logs and DB readiness. M2 removes mail-adapter invocation from API services, adds full-state queue snapshots, desired/observed revisions, a separate pending worker, lease recovery/fencing, bounded retry/dead letter, manual and scheduled reconciliation, tenant-scoped visibility/retry and Operations UI.

PostgreSQL queue/outbox was chosen for atomicity and lower operational complexity; provider calls execute outside transactions and outside the API. Automated evidence covers concurrency/revocation, rollback of resource/job/audit, legacy backfill, failure/recovery and UI semantics. See [verification](VERIFICATION.md) for exact counts/commands. These are local foundations, not live mail or production certification.

The initial M3 isolated provider spike has passed. Continue with the secure-foundation milestone above; public infrastructure and all M4–M10 acceptance gates remain open.
