# Secure mail integration foundation

14 October 2026. Implemented only in the isolated, digest-pinned DMS 15.1.0 lab. API/default worker remain pending-only. This document supersedes the earlier agent and suspension design where they differ; it does not approve production integration.

## Suspension decisions

Authentication and inbound acceptance are independent policy dimensions, each with desired revision and actual observation. Existing SaaS `suspended` means **authentication disabled**, never deletion. The lab-only optional `inboundPolicy` is `accept` or `defer`; absence means accept for historical job compatibility. Adding these dimensions to public APIs, database snapshots and UI requires an additive migration and owner policy review; no public capability was enabled here.

| Policy | SMTP inbound | IMAP / authenticated SMTP submission | Stored mail / reactivation |
| --- | --- | --- | --- |
| Fully active | Normal recipient checks and delivery; quota still applies | New logins allowed | Existing mail preserved |
| Authentication disabled, receive allowed | Accepts and stores valid local messages | New logins denied; Dovecot sessions kicked | Account/hash/mail remain; restore login without password replacement |
| Inbound deferred, authentication enabled | Recipient receives `450 4.2.1` at RCPT, before DATA | New logins allowed | Mail readable; sender retries after reactivation |
| Both restricted | Same temporary SMTP deferral | New logins denied; sessions kicked | No mailbox deletion; both policies independently reversible |

The lab uses a Dovecot deny passdb before normal passdb and a Postfix `check_recipient_access texthash:` restriction placed before permit rules in recipient restrictions. The map returns explicit 450; it never uses DISCARD or an accepting sink transport. The persistent DMS `postfix-main.cf` override is necessary because startup regenerates effective configuration. Independent inspect reads the effective Postfix restriction and map; protocol probes remain the authoritative acceptance test.

Queued-message contract: messages already accepted with SMTP 250 before the policy change remain the receiver's responsibility and may still deliver into the preserved mailbox. This RCPT policy does not freeze the existing Postfix/LMTP queue. Messages refused with 450 have not been accepted; the sending MTA owns retries and eventual expiry/bounce under its policy. Reactivation permits a new delivery attempt; it cannot recover messages whose sender queue has already expired. Existing authenticated SMTP sessions may retain authorization and require a separate reviewed session invalidation mechanism. Alias expansion, catch-all, forwarding to a restricted account, alternate transports, multiple nodes and multi-recipient transactions require additional tests before claiming universal enforcement. The lab proves direct local recipients only.

## Agent decisions and residual authority

The Unix listener now runs as dedicated numeric UID **3001**, GID **3000**, empty supplementary groups, with no inherited Linux capabilities after dropping root. Worker identity remains UID1000/GID3000 plus bearer token, enforced through SO_PEERCRED and constant-time comparison. UID3001 is distinct from the worker and mail daemons; it cannot read root-only seed/account/state files. Code and bindings are read-only mounts. Numeric lab identities need explicit conflict-free service-account allocation in production.

A separate root **lab provider helper** retains the DMS-owned file/reload/kick authority. Its sole RPC channel is an inherited socketpair to its child, with no filesystem helper socket or TCP port. It independently validates operation, schema and trusted mailbox binding. No worker-supplied command, executable, path, container, password or hash is accepted. Frontend death closes the channel; helper death terminates the frontend. The global lock serializes shared FILE-provisioner state; fsynced acceptance journal and revision checks apply to inbound policy changes too. Historical accept-policy snapshots remain replay-compatible.

This reduces the listener's immediate privileges, but a compromised authorized listener can still request allowed operations on the entire closed lab inventory. The helper remains root and is **not an approved production sandbox**. Production needs a separately packaged helper, mandatory access-control profile, capability/filesystem/syscall restrictions, protected journal lifecycle and backup rollback fencing, runtime UID allocation, authorization provisioning/revocation and independent security review. Do not copy this lab service into production.

Atomic writes use random exclusive O_NOFOLLOW temporary files and reject symlink destinations/parents. Fixed configuration/state parents are trusted and root-owned; no tenant path reaches the filesystem API. This is not protection against a malicious node root replacing ancestor directories. Security stdout records only event, status and allowlisted result code; no headers, request body, address, provider exception or credential. Durable centralized security-log retention/integrity remains future work. No Docker socket or generic shell execution is exposed.

## Credential architecture decision (design only)

Dashboard credentials stay in the dashboard authentication system. A mailbox receives a separate user-chosen password; dashboard hashes are never copied. Recommend a version-pinned Dovecot-native ARGON2ID generator, using stdin and captured output, after cost/DoS benchmarking. New synthetic lab accounts now use this native scheme. The earlier raw Node Argon2 import failure remains a compatibility finding; no custom encoding transformation is part of the production design. [Dovecot's password scheme documentation](https://doc.dovecot.org/2.3/configuration_manual/authentication/password_schemes/) documents native schemes and stdin generation.

Proposed setup/reset/rotation sequence, not implemented:

1. Reauthenticate the dashboard actor, require appropriate mailbox ownership/admin permission and MFA for privileged reset. Explicitly separate the mailbox user from the administrator who initiates access. Reauthorize when consuming a grant, including membership revocation and mailbox/node assignment. Rate-limit and audit issuance without revealing account existence to unauthenticated callers.
2. Generate a high-entropy opaque single-use grant with a standard CSPRNG. Store only its digest, mailbox/tenant, intended recipient/actor, purpose, credential generation, expiry and consumed state. Use a short reviewed TTL (proposal: 15 minutes), bounded attempts and atomic consumption. New grant/revocation invalidates older grants. Do not put bearer grants in audit, queue, query logs or referrers. Prefer an authenticated setup page with no third-party content and CSRF protection. Owner must choose how the intended mailbox user receives proof of access; a mailbox not yet usable cannot be its own sole recovery channel.
3. Submit the chosen password over authenticated HTTPS; disable body tracing at proxy/APM/application layers and caching. Keep plaintext only in bounded process memory; reject line breaks/NUL if invoking the interactive native stdin tool. No plaintext argv, environment, subprocess exception output, DB/queue/audit/log entries or job result. Process memory cannot be promised zeroized by Python/Node; isolate the handler and minimize lifetime/core dumps.
4. The restricted credential service generates a provider-native hash, with bounded concurrency, timeouts and a tested parameter policy. A private same-host socket or authenticated encrypted cross-host transport carries the sensitive artifact; no invented cryptographic protocol. Provisioning workers receive only an opaque scoped reference and credential generation. Secret-provider ACLs bind the reference to mailbox, target node, purpose and expiry, never to tenant-selected paths or arbitrary credentials.
5. Where asynchronous recovery requires retention, store the hash as sensitive credential material in a managed secret provider or envelope-encrypted database field using maintained cryptographic libraries/KMS, authenticated metadata and separate access roles. Keep encryption keys outside the metadata database and backups; audit access, rotate keys, enforce retention and revoke obsolete references. Avoid retained plaintext entirely. Password hashes still permit offline attacks and require restricted access. The provider necessarily persists its supported hash in protected account/passdb storage and encrypted backups.
6. Persist acceptance of the credential generation before provider effects, fence older generations remotely, serialize with suspension/rename/node migration, and atomically replace the hash. A crash-after-effect retry uses the same scoped artifact; it cannot restore an older password. Verify provider state without retaining or returning plaintext; synthetic tests may authenticate, but production success cannot require a password readback. A verification handle can be a protected artifact generation/digest plus provider inspection. It is not authentication proof unless the provider supplies that capability.
7. Return only status/generation. Do not automatically undo an administrator's authentication suspension when a password changes. Invalidate previous grants/references and explicitly revoke existing sessions under reviewed IMAP/SMTP semantics. Notify the user through the approved independent channel without including the password. Never email a reusable password. Recovery and administrator reset require audited, expiring authorization, with support access separate from organization privileges.

No credential setup endpoint, grant table, KMS dependency, real secret storage or reusable job secret was added. The lab seed/HMAC generator remains synthetic-only and must be removed from any production design. Owner decisions are required for recipient proof/recovery, MFA requirements, hash cost, service/transport trust, secret-provider choice, encryption keys and retention.

## Verification and limits

Executed outcomes, failure discovered/corrected, commands and reviewed machine evidence are in [SECURE_MAIL_RESULTS.md](SECURE_MAIL_RESULTS.md).

The worker now always performs idempotent ensure before acknowledgement, even when initial inspect matches desired state. Matching quota/status alone cannot establish acceptance of a new remote revision; skipping ensure left a late older operation able to undo a newly acknowledged intent. A regression checks matching-state recovery still establishes the fence and rejects a delayed older target. Provider convergence now requires repeated stable observations after a settling interval for the pinned 1-second FILE watcher. This addresses the observed intermediate-snapshot race locally; a timing window is not a production atomicity guarantee or a substitute for a provider generation acknowledgement.

`security_tests.py prepare` exercises actual TLS IMAP/submission with native ARGON2ID, rejected secret/command fields, wrong peer UID, wrong token, unknown operation, symlink refusal, authentication-only suspension with stored inbound delivery, inbound-only deferral with login allowed, combined restriction, replay/conflicting-policy/stale revision rejection. `restart` must run after an actual container restart; it checks policy/auth/fence persistence and successful redelivery/reactivation with stored mail preserved. The full fail-fast runner now includes both phases before all prior conformance scenarios.

Before production: complete credential flow implementation and adversarial replay/revocation/expiry testing; limit and independently review the privileged helper; cover routing/aliases/existing sessions/queues; evaluate filtering/abuse/TLS/network isolation under load; encrypt off-host backups and test coordinated restoration of DB, mail, credential generations and fencing. No local scenario establishes production readiness.

## Exact owner decisions and next milestone

- Choose intended mailbox-user identity proof, setup/reset delivery and recovery channels, MFA and support-reset authority; approve credential retention/KMS/secret-provider and key ownership.
- Approve business suspension policy: authentication only versus inbound temporary deferral, notification/grace period, retention and queue-expiry expectations. A billing event must never imply silent message disposal.
- Approve a concrete production helper isolation/transport/identity design and journal restore policy before deploying it.
- Select final provider/topology after equivalent candidate tests and measured filtered load; approve costs, backup destination/retention/RPO/RTO and operational ownership.
- Public IP/port/PTR, DNS, VPS, production secrets, live accounts/mail and deployment remain separately approval-gated; none changed here.

Next engineering milestone: implement a synthetic-only, single-use credential grant/reference lifecycle with transactional generation fencing, expiry/revocation/recovery tests, and independently sandbox the provider helper. Then review the concrete design and test evidence before any real credential or infrastructure activation.
